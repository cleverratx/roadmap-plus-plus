# Выкладка на сервер

Здесь описано, как поднять Roadmap++ на своём VPS с HTTPS, как выкладывать новые версии, как устроены бэкапы и как из них восстановиться. Всё это нужно сделать до того, как в сервисе появятся настоящие данные.

## Как это устроено

На сервере работают четыре контейнера:

| Контейнер | Что делает |
|---|---|
| `caddy` | единственный, кто смотрит в интернет: принимает 80 и 443, сам получает и продлевает сертификат Let's Encrypt, переводит HTTP на HTTPS и добавляет заголовки безопасности |
| `nginx` | отдаёт собранный фронт и проксирует `/api` в API |
| `api` | бэкенд на .NET, при старте сам применяет миграции |
| `db` | PostgreSQL, наружу не открыт вообще |

Основной `compose.yaml` общий для всех, а для сервера к нему добавляется `deploy/compose.prod.yaml` с Caddy. Файл `compose.override.yaml` нужен только для локальной разработки и на сервере не подключается, поэтому ни база, ни Nginx на сервере наружу не торчат.

Cookie сессии в режиме Production всегда уходит с флагом `Secure`, то есть браузер отправляет его только по HTTPS. Caddy добавляет `Strict-Transport-Security`, и после первого визита браузер сам будет ходить на сайт только по HTTPS. Адрес и протокол клиента Caddy передаёт дальше через `X-Forwarded-For` и `X-Forwarded-Proto`, а Nginx пропускает их в API без изменений. Это важно для ограничения частоты входа: оно считается по IP клиента, и без этого все пользователи выглядели бы для API как один адрес Caddy.

## Что понадобится

- VPS на Linux с 1-2 ГБ памяти, например Ubuntu 24.04 или Debian 12;
- домен, у которого A-запись (и AAAA, если есть IPv6) указывает на сервер;
- открытые порты 80 и 443: через 80 Let's Encrypt проверяет, что домен ваш;
- Docker с плагином compose и git.

## Первая выкладка

Код кладём в `/opt/roadmap-plus-plus`: этот путь прописан в таймере бэкапов. Если хочется другой, поправьте его в `deploy/systemd/roadmap-backup.service`.

```bash
sudo git clone https://github.com/<владелец>/roadmap-plus-plus.git /opt/roadmap-plus-plus
cd /opt/roadmap-plus-plus
sudo cp .env.example .env
sudo chmod 600 .env
```

Дальше заполните `.env`:

- `POSTGRES_PASSWORD` задайте длинным и случайным, например из `openssl rand -hex 32`. Пароль из примера годится только для локальной разработки;
- `DOMAIN` это домен сервиса без `https://`, например `roadmap.example.com`;
- `ACME_EMAIL` это почта, куда Let's Encrypt напишет, если с сертификатом что-то пойдёт не так;
- `HTTP_PORT` и `DB_PORT` на сервере не используются, их можно не трогать.

После этого запускаем выкладку:

```bash
sudo bash deploy/scripts/deploy.sh
```

Скрипт заберёт свежий `main`, соберёт образы, поднимет контейнеры и дождётся, пока API ответит `Healthy`. При первом запуске Caddy получит сертификат, на это уходит до минуты. Потом сайт откроется на `https://<ваш домен>`.

## Обновление и откат

Новая версия выкладывается той же командой:

```bash
sudo bash deploy/scripts/deploy.sh
```

Перед выкладкой скрипт сам снимает дамп базы с меткой `before-deploy`. Если в каталоге на сервере есть незакоммиченные правки, скрипт остановится, чтобы их не затереть.

Чтобы выложить конкретную версию, например откатиться на прошлый коммит, передайте её:

```bash
sudo bash deploy/scripts/deploy.sh <коммит или тег>
```

Откат кода работает, только если новая версия не меняла схему базы. Миграции применяются при старте API и обратно сами не откатываются. Если новая версия успела применить миграцию и что-то пошло не так, откатите код и восстановите базу из дампа `before-deploy`, как описано ниже.

## Бэкапы

Бэкап снимает `deploy/scripts/backup.sh`. Он делает `pg_dump` и сразу проверяет, что дамп восстанавливается: разворачивает его во временную базу рядом с рабочей, убеждается, что на месте история миграций и таблицы, пишет, сколько там пользователей, команд и узлов, и удаляет временную базу. Дамп, который не прошёл проверку, не сохраняется, а скрипт завершается с ошибкой. Так мы узнаём о сломанном бэкапе в тот же день, а не в день, когда он понадобится.

Дампы лежат в `backups/` в корне репозитория, доступны только root и хранятся 14 дней. Срок и каталог настраиваются в `.env`:

- `BACKUP_KEEP_DAYS` задаёт, сколько дней хранить дампы;
- `BACKUP_DIR` задаёт, куда их класть;
- `BACKUP_RSYNC_TARGET` задаёт, куда ещё скопировать каждый дамп через rsync, например `backup@storage.example.com:/srv/roadmap/`.

Последнюю настройку очень советуем заполнить. Бэкап на том же сервере спасает от ошибки в коде или случайного удаления, но не от смерти самого VPS. Для rsync понадобится SSH-ключ root без пароля, добавленный на сервер для бэкапов.

Чтобы бэкап снимался каждый день, включите таймер systemd:

```bash
sudo cp deploy/systemd/roadmap-backup.service deploy/systemd/roadmap-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now roadmap-backup.timer
```

Таймер срабатывает в 03:30 по времени сервера, с разбросом до 15 минут. Если сервер в это время был выключен, бэкап снимется сразу после включения. Проверить, когда был последний запуск и чем он закончился:

```bash
systemctl list-timers roadmap-backup.timer
journalctl -u roadmap-backup.service -n 50
```

Снять бэкап руками можно в любой момент:

```bash
sudo bash deploy/scripts/backup.sh
```

## Восстановление

```bash
sudo bash deploy/scripts/restore.sh backups/roadmap-20261109-033012.dump
```

Скрипт попросит ввести имя базы, чтобы случайно не затереть её не тем файлом. Дальше он:

1. проверяет дамп во временной базе так же, как при бэкапе;
2. снимает страховочный дамп текущей базы с меткой `before-restore`, так что передумать можно и после восстановления;
3. останавливает API, пересоздаёт базу из дампа и запускает API снова;
4. ждёт, пока API ответит `Healthy`.

Сессии и ключи шифрования cookie хранятся в той же базе, поэтому после восстановления всё вернётся в состояние на момент дампа, включая то, кто где был залогинен.

Если сервер умер целиком, порядок такой: поднять новый VPS по разделу "Первая выкладка" с тем же `.env`, скопировать на него последний дамп из места, куда его копировал rsync, и запустить `restore.sh`.

## Как проверить боевую сборку у себя

Всё то же самое можно поднять локально, только вместо настоящего домена указать `localhost`. Тогда Caddy выпустит сертификат своим внутренним центром сертификации, и браузер предупредит, что не доверяет ему. Чтобы не трогать локальную базу для разработки, запускайте под отдельным именем проекта:

```bash
COMPOSE_PROJECT_NAME=roadmap-prod-check DOMAIN=localhost ACME_EMAIL=me@example.com \
  bash deploy/scripts/deploy.sh --current
```

`--current` выкладывает то, что уже лежит в каталоге, без git. Убрать за собой всё, включая тома с базой и сертификатами:

```bash
COMPOSE_PROJECT_NAME=roadmap-prod-check DOMAIN=localhost ACME_EMAIL=me@example.com \
  docker compose -f compose.yaml -f deploy/compose.prod.yaml down -v --rmi local
```

На Windows встроенный `curl` (он работает через schannel) рвёт соединение с локальным сертификатом Caddy. Браузер, Node и curl из WSL или из контейнера при этом работают нормально, а на Linux-сервере проблемы нет.

Этот же сценарий на каждом PR, который трогает `deploy/`, compose-файлы или Dockerfile, проверяет CI в [deploy.yml](../.github/workflows/deploy.yml): поднимает сборку с HTTPS, проверяет редирект с HTTP, флаг `Secure` у cookie и HSTS, снимает бэкап, заводит пользователя после бэкапа, восстанавливается и убеждается, что этого пользователя больше нет, а первый на месте. В конце он выкладывает версию повторно поверх живой базы.
