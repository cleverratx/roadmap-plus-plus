# Ветки, коммиты и PR

`main` всегда собирается и проходит CI, поэтому напрямую в него не коммитим: любая работа идёт в короткой ветке и вливается через PR. На `main` включена защита, она требует PR и зелёные проверки:

- `backend` из [backend.yml](../.github/workflows/backend.yml): формат кода, сборка, актуальность OpenAPI-документа и тесты;
- `frontend` из [frontend.yml](../.github/workflows/frontend.yml): актуальность клиента API, линтер, тесты, проверка типов и сборка.

Предупреждения в обоих считаются ошибками.

Есть и третья проверка, `deploy` из [deploy.yml](../.github/workflows/deploy.yml). Она поднимает боевую сборку с HTTPS, снимает бэкап, восстанавливает из него базу и выкладывает версию повторно. Запускается она только тогда, когда PR трогает `deploy/`, compose-файлы или Dockerfile, поэтому обязательной в защите `main` её не делаем: иначе PR без таких правок ждал бы её вечно. Если она запустилась, вливаем только после того, как она позеленеет.

## Как назвать ветку

Шаблон такой: `<тип>/<область>-<суть>`, а если есть issue, то `<тип>/<номер>-<область>-<суть>`.

```
chore/backend-skeleton
test/arch-module-boundaries
feat/planning-item-tree
feat/23-frontend-timeline-zoom
fix/interchange-md-escaped-pipes
spike/frontend-timeline-d3-vs-vis
docs/adr-0001-task-table-source
```

| Тип | Когда |
|---|---|
| `feat` | новая возможность |
| `fix` | исправление ошибки |
| `refactor` | переделка без изменения поведения |
| `test` | только тесты |
| `docs` | README, ADR, описания форматов |
| `ci` | GitHub Actions |
| `chore` | каркас, зависимости, настройки, Docker и прочая инфраструктура |
| `spike` | прототип или эксперимент; обычно его не вливают, итогом становится вывод в ADR или issue, а код потом пишется начисто |

| Область | Что затрагивает |
|---|---|
| `identity`, `planning`, `knowledge`, `interchange`, `assistant`, `notifications` | модуль вместе с его `Contracts` и тестами |
| `api` | Bootstrapper: `Program.cs`, middleware |
| `blocks` | `BuildingBlocks` |
| `arch` | архитектурные тесты и правила границ модулей |
| `backend`, `frontend` | бэкенд или фронтенд целиком: решение, сборка, общие настройки, UI-кит |
| `deploy` | compose, Dockerfile, Nginx, скрипты |
| `adr-NNNN`, `formats`, `readme` | документация |

В имени ветки только латиница в нижнем регистре, цифры и дефисы, без кириллицы, пробелов и `_`. Суть это 2-4 английских слова о том, что именно делаем: `planning-item-tree` хорошо, а `yaroslav-work` или `fix-2` плохо, по ним через неделю никто не вспомнит, что там было.

Если фича задевает и API, и экран, она всё равно живёт в одной ветке, и область у неё модульная, например `feat/planning-item-crud`. Область `frontend` оставляем для того, что ни к какому модулю не привязано: таймлайн, UI-кит, роутер.

## Как назвать коммит и PR

Коммиты и PR называем по одному шаблону: `<тип>(<область>): <что сделано>`. Тип и область берём из имени ветки, но без сути и без номера issue. Для ветки `chore/frontend-api-client` префикс получится `chore(frontend):`, для `feat/23-frontend-timeline-zoom` будет `feat(frontend):`, а для `docs/adr-0004-auth` будет `docs(adr-0004):`. Номер issue при этом не теряется, он уходит в описание PR.

После двоеточия пишем по-русски, с маленькой буквы и без точки в конце. Описываем результат, то есть что появилось или изменилось, а не процесс: "клиент api и unwrap с HttpError" хорошо, а "добавил клиент" или "работа над клиентом" хуже. Названия библиотек, классов и команд оставляем как есть, по-английски. Хорошо, если заголовок укладывается примерно в 72 символа: дальше его обрезают и GitHub, и `git log --oneline`, а подробности всё равно удобнее читать в описании.

### Коммиты в ветке

Все коммиты в ветке начинаются с того же префикса, что и сама ветка, а текст после двоеточия рассказывает про конкретный шаг. Даже мелкие правки по ревью называем по шаблону и пишем, что именно поправили, например `chore(frontend): понятная ошибка, если API не ответил`. Если какому-то коммиту хочется дать другой тип или другую область, скорее всего, эта работа просится в отдельную ветку.

### Заголовок PR

У PR тот же префикс, а текст после двоеточия обобщает все коммиты ветки. Он отвечает на вопрос "что даёт эта ветка целиком" и не повторяет последний коммит. Это важно, потому что вливаем через Squash and merge, и заголовок PR становится единственным коммитом в `main`, по которому потом читают историю проекта.

Например, в ветке `chore/frontend-api-client` могли быть такие коммиты:

```
chore(frontend): генерация OpenAPI-документа при сборке бэкенда
chore(frontend): openapi-typescript и скрипт api:generate
chore(frontend): клиент api и unwrap с HttpError
chore(frontend): проверка актуальности документа и клиента в CI
```

А заголовок PR, который станет коммитом в `main`, их обобщает:

```
chore(frontend): типизированный клиент API из OpenAPI-документа бэкенда
```

Заголовки вроде `fix`, `правки`, `WIP` или `chore(frontend): обновление` не годятся: по ним через месяц никто не поймёт, что изменилось. `Feat(Frontend): Added API client` тоже не подходит, тут сломан шаблон: тип и область пишем строчными, а текст по-русски.

В описании PR коротко пишем, что сделано, как проверяли и на что стоит посмотреть ревьюеру. Если PR закрывает issue, добавляем `Closes #23`.

## Как вливаем

Одна ветка решает одну задачу и превращается в один PR. Ветка живёт дни, а не недели, создаётся от свежего `main` и удаляется после слияния.

Вливаем через Squash and merge, так что в `main` попадает ровно один коммит с заголовком PR в качестве сообщения. Перед слиянием стоит ещё раз перечитать заголовок: за время ревью ветка могла подрасти, и он должен описывать то, что в итоге в неё вошло.
